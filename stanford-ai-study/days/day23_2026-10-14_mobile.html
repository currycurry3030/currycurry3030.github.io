🔁 Deep Dive · 실제 DOE 결과가 지식으로 되돌아오는 순간

Advisor Recommendation{candidate, predicted Δmetrics, uncertainty, evidence}↓Engineer selects / edits candidate↓DOE / Evaluation performed↓Actual Metrology / FDC result↓Prediction Error + Constraint outcome + Engineer interpretation↓NEW Evaluation Event↓Knowledge Extraction Harness↓NEW Evaluation Case → Process Memory

이 loop가 있어야 Advisor가 단순 검색 앱이 아니라 평가 경험이 축적되는 시스템이 됨. 단, 실제 결과가 들어왔다고 자동으로 semantic rule을 갱신하지 않고 Case로 먼저 보존.

🎯 오늘의 목표

  • 실제 DOE/Metrology 결과를 recommendation prediction과 비교하고, 그 결과를 새 Evaluation Case로 다시 capture.
  • 핵심 용어 4개를 한국어로 설명한다.
  • SQL/분석 결과로 hypothesis를 accept/reject하고 re-plan.

🧩 핵심 개념

Execution feedback

code/test/SQL/tool 결과를 모델 밖의 실제 observation으로 사용한다.

Hypothesis testing

가설별로 예상 evidence를 정의하고 실제 관측과 비교한다.

Re-plan

새 evidence가 기존 plan을 반박하면 다음 step을 바꾼다.

Tool vs task error

tool 호출 실패와 tool은 성공했지만 가설이 틀린 것을 구분한다.

🧭 Mental Model

hypothesis → discriminating test → execute → observe → accept/reject → re-plan

실무 연결: 실제 DOE/평가 후 Metrology 결과가 돌아오면 기존 recommendation의 가설과 예측을 비교해 Process Memory에 새 Evaluation Case로 축적하고 다음 추천의 grounding으로 재사용한다.

주의: query가 성공했다는 사실과 가설이 지지됐다는 사실을 혼동하지 않는다.

🛠 20분 실습

  1. 가상 DOE 결과를 받아 predicted Δmetric과 실제 결과를 비교하고 새 Evaluation Case로 축적하는 loop 설계.
  2. 정상 동작 예시 1개를 만든다.
  3. 실패/edge case 1개를 만든다.
  4. 오늘 결과를 5줄로 요약한다.
