Cross-loopEvaluation System

Extraction·Retrieval·Tool Safety·Prediction·Candidate·Provenance를 계층별 평가

Loop 1 · Capture
Evaluation Event → Case → Process Memory
Loop 2 · Decision
Context → Cases → Candidates → Verify
Loop 3 · Improve
Actual Result → New Case → System Update

📏 Deep Dive · 하나의 Agent Score 대신 계층형 Eval

Layer질문예시 Metric
Capture평가 맥락을 정확히 Case로 뽑았나?field accuracy, evidence attribution, schema validity
Retrieval현재 상황에 필요한 과거 Case를 찾았나?Recall@k, applicability precision, evidence coverage
Tool / QueryDB를 안전·효율적으로 조회했나?guardrail violation, scan bytes, truncation, latency
PredictionΔrecipe → Δmetric/constraint 예측이 맞나?error, calibration, OOD detection
Recommendation좋은 Top-k DOE 후보를 냈나?constraint pass, top-k utility, robustness/diversity
Grounding근거가 실제 evidence에 연결됐나?provenance correctness, unsupported claim rate
Human usefulness엔지니어가 실제 검토 가능한가?accept/edit/reject, time saved, preference

원칙: LLM-as-a-Judge는 열린 설명 품질에 보조적으로 사용하고, 가능한 것은 deterministic check로 평가.

🎯 오늘의 목표

  • request/environment/stopping criteria/scorer 4-tuple과 code grader, LLM-as-judge.
  • 핵심 용어 4개를 한국어로 설명한다.
  • 10~20개 eval case + scorer로 eval.py 작성.

🧩 핵심 개념

Eval task fixture

request와 초기 environment를 고정해 재현 가능한 task를 만든다.

Stopping criteria

max turns/time/tool budget/final state 등 평가 종료 조건이다.

Deterministic grader

정답·DB state·file diff·unit test 등으로 자동 검증한다.

LLM judge

rubric 기반으로 열린 설명 품질을 평가하지만 bias를 관리해야 한다.

🧭 Mental Model

fixture → run agent → capture trajectory → deterministic checks → optional judge → failure tag

실무 연결: Eval은 ① Evaluation Case 추출 정확성 ② retrieval grounding ③ query/tool 안전성 ④ Δmetric/constraint 예측 ⑤ Top-k candidate 유용성 ⑥ evidence/provenance ⑦ abstention/uncertainty를 분리해 본다.

주의: 최종 score만 저장하지 말고 trajectory와 failure taxonomy를 함께 남긴다.
