"agent에 메모리를 붙였다"는 말은 대개 대화 기록을 저장했다는 뜻입니다. 그런데 대화 기록은 메모리의 한 종류일 뿐이고, 대부분의 실무 문제에서는 가장 덜 중요한 종류입니다. CS329Z의 memory 파트를 정리하며 이 구분을 다시 잡았습니다.

## 네 가지 메모리

사람의 기억에 비유하면 책상 위 메모, 과거 일지, 교과서 지식이 서로 다른 것처럼 agent memory도 나뉩니다.

| 종류 | 내용 | 수명 |
|---|---|---|
| Working | 현재 task의 context | 요청 단위 |
| Episodic | 과거에 실제 일어난 사건 | 장기 |
| Semantic | 여러 사건에서 일반화된 지식 | 장기, 검증 필요 |
| External | 외부 시스템의 데이터 | 시스템 소유 |

중요한 건 각 종류마다 **쓰기/읽기/만료 정책이 다르다**는 점입니다. 이걸 한 덩어리로 취급하면 "오래된 대화가 계속 끌려나와 판단을 방해하는" 문제가 생깁니다.

대화 기록은 대체로 working memory의 부산물입니다. 축적할 가치가 있는 건 보통 episodic memory 쪽입니다.

## 사후 정리로는 맥락이 복원되지 않는다

지식을 나중에 문서로 정리하면 되지 않나 싶지만, 며칠 지나 회의록을 복기해 쓰는 것과 실험 직후에 기록하는 것은 내용이 다릅니다. 빠지는 건 대체로 이런 것들입니다.

- 왜 그 시도를 했는지 (intent)
- 당시 조건이 정확히 무엇이었는지 (conditions)
- 왜 그렇게 해석했는지 (interpretation)

결론만 남고 판단 맥락이 사라집니다. 그래서 capture 시점을 뒤로 미루지 않고, 평가가 발생하는 순간에 사람의 코멘트와 시스템의 근거 데이터를 함께 붙잡습니다. 사람이 남긴 노트와 DB의 증거를 join key로 묶어 하나의 구조화된 기록으로 만드는 단계가 필요합니다.

## Evaluation Case를 source of truth로

여기서 핵심 설계 결정이 나옵니다. **모델이 만든 요약이 아니라, 출처에 연결된 사건 기록이 source of truth여야 합니다.**

LLM으로 문서를 요약해 벡터 DB에 넣는 구성은 흔합니다. 문제는 그 요약이 틀렸을 때 검증할 원본 경로가 없다는 것입니다. 요약의 요약이 쌓이면 시스템은 자기가 만든 말을 근거로 다시 판단하게 됩니다.

그래서 case를 "결론 한 줄"이 아니라 실험 카드 전체로 저장합니다. intent, conditions, delta, result, interpretation, conclusion, evidence/provenance가 한 단위입니다.

그리고 수정 이력을 남깁니다. 결론이 바뀌어도 원천 result와 evidence는 덮어쓰지 않습니다. immutable한 사건 코어 위에 검토된 주석을 얹는 구조입니다. "그때는 왜 그렇게 판단했는가"를 나중에 추적할 수 있어야 합니다.

> 사건은 불변, 해석은 버전 관리. 이 둘을 같은 필드에 저장하면 지식의 신뢰도를 잃습니다.

## 한 번의 성공을 법칙으로 만들지 않기

episodic에서 semantic으로의 승격이 가장 조심스러운 단계입니다. 한 번 통한 방법을 "항상 통하는 규칙"으로 만들면, 시스템은 빠르게 자신감 있고 틀린 상태가 됩니다.

승격 전에 확인할 것들입니다.

1. 유사 사례가 반복되는가
2. 조건이 일관적인가
3. 반례가 있는가
4. 도메인 전문가가 검증했는가

그리고 semantic knowledge는 반드시 원래 case와 evidence로 back-link합니다. 적용 조건, 예외, 근거 case ID를 함께 저장하지 않은 일반화는 나중에 검증할 수 없습니다.

## 삭제보다 상태 표시

공정이나 정책이 바뀌면 과거 사례가 더 이상 유효하지 않게 됩니다. 이때 지우고 싶어지지만, 오래된 매뉴얼을 버리는 것보다 "현재 사용 금지, 새 버전은 이것"이라고 표시하는 편이 낫습니다.

- `deprecated_context`로 표시하되 이력은 보존
- retrieval score에는 반영해서 상위에 오지 않게
- 충돌이 있으면 최신성만으로 자동 판정하지 않고 조건 차이를 비교

audit 관점에서도 그렇지만, 실용적으로도 "예전에는 이렇게 했는데 왜 바꿨는지"가 종종 가장 가치 있는 지식입니다.

## 사람과 agent가 같은 저장소를 본다

마지막으로 흔한 실수 하나. 사람이 읽을 위키와 agent가 읽을 벡터 DB를 따로 만드는 것입니다. 처음에는 편하지만 곧 두 지식이 갈라지고, 어느 쪽이 맞는지 아무도 모르게 됩니다.

표현 계층만 나누고 저장소는 하나로 둡니다.

- 사람용 뷰: 타임라인, 검색, 5분 요약 렌더링
- agent용 인터페이스: structured retrieval, evidence pointer

사람에게는 읽기 좋은 책장이, agent에게는 API가 필요하지만 책의 내용은 하나여야 합니다. 지식의 복사본을 만들지 않는 것이 원칙입니다.

## 정리

- 대화 기록 ≠ 메모리. working/episodic/semantic/external은 정책이 다르다
- 맥락은 사건이 일어나는 순간에만 온전히 잡을 수 있다
- 모델 요약이 아니라 출처에 연결된 사건 기록이 source of truth
- 사건은 불변, 해석은 버전 관리
- 일반화는 반복·일관성·반례·검증을 통과한 뒤에
- 삭제보다 superseded 표시
- 사람과 agent는 표현만 다르게, 저장소는 하나로
