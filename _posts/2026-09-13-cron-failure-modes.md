자동화를 붙여놓고 한 달쯤 지나면 이런 질문이 떠오릅니다. "이거 지금 돌고 있나?" 정기 실행 작업 8개를 한 달간 굴린 실행 로그 62건을 전부 열어서 세어봤습니다. 이 글이 답하려는 질문은 하나입니다. **에이전트 정기 작업은 어디서 죽는가, 그리고 왜 죽은 걸 모르는가.**

결론부터 쓰면, 가장 위험한 실패는 에러를 던지는 실패가 아니었습니다.

## 실행 로그 62건을 분류해보니

상태별로 나누면 이렇습니다.

| 상태 | 건수 |
|---|---:|
| 정상 종료 | 55 |
| silent (빈 출력) | 4 |
| script failed (0이 아닌 종료코드) | 3 |

숫자만 보면 정상률 88%입니다. 그런데 작업 단위로 다시 묶으면 그림이 완전히 달라집니다.

| 작업 | 정상 | silent | failed |
|---|---:|---:|---:|
| 일일 브리핑 | 23 | 0 | 0 |
| 평일 전략 검증 | 20 | 0 | 0 |
| 평일 가격 트래킹 | 5 | 0 | 0 |
| 블로그 새 글 감지 | 4 | 0 | 0 |
| 주말 스캔 | 2 | 0 | 0 |
| 주간 리포트 | 1 | 0 | 1 |
| **데이터 자동 적재** | **0** | **4** | **2** |

한 작업이 6번 실행되는 동안 **단 한 번도 성공하지 못했습니다.** 전체 정상률 88%는 이 사실을 완벽하게 가리고 있었습니다. 지표를 실행 단위로 집계하면 자주 도는 건강한 작업이 드물게 도는 병든 작업을 덮습니다. 작업 단위 성공률을 따로 보지 않으면 이걸 못 봅니다.

## 실패 유형 1: 던지는 실패

가장 다루기 쉬운 종류입니다. 종료 코드가 0이 아니고 stderr에 원인이 남습니다.

```
Script exited with code 1
stderr:
7z extraction failed (wrong password?): ERROR: Wrong password : <파일명>.xlsx
```

암호화된 내보내기 파일을 푸는 단계에서 비밀번호가 맞지 않았습니다. 원인이 한 줄로 찍혀 있으니 고치는 건 어렵지 않습니다. 다른 하나도 비슷했습니다.

```
RuntimeError: TELEGRAM_BOT_TOKEN is missing from telegram.env
```

이건 더 재미있는 케이스입니다. 토큰 파일은 존재했고 값도 들어 있었습니다. 문제는 파일에 `export TELEGRAM_BOT_TOKEN=...` 형식으로 적혀 있었는데, 파서가 `TELEGRAM_BOT_TOKEN=` 으로 시작하는 줄만 찾고 있었다는 겁니다. 셸에서 `source` 하면 잘 되는 파일이 파이썬 파서에서는 안 읽혔습니다.

교훈은 이겁니다. **사람이 쓰는 경로(셸 source)와 자동화가 쓰는 경로(직접 파싱)가 다르면, 사람이 확인했을 때 멀쩡한 것이 자동화에서는 깨집니다.** 설정을 검증할 때는 반드시 자동화가 실제로 쓰는 경로로 검증해야 합니다.

## 실패 유형 2: 조용한 실패

진짜 문제는 이쪽입니다. `silent (empty output)` 4건.

종료 코드는 0입니다. 에러도 없습니다. 그런데 아무 출력도 없습니다. 스크립트 입장에서는 "처리할 입력 파일이 없어서 할 일이 없었다"에 가까운 상태였고, 정상 종료했습니다. 기술적으로 틀린 동작이 아닙니다.

문제는 **"할 일이 없었다"와 "할 일을 못 찾았다"가 구분되지 않는다**는 점입니다. 앞의 것은 정상이고 뒤의 것은 장애인데, 둘 다 조용히 0으로 끝납니다. 실패 알림만 걸어둔 시스템은 이 4건을 영원히 못 봅니다.

이 구분을 코드에 넣는 건 어렵지 않습니다.

```python
files = find_export_files(EXPORT_DIR)

if not files:
    # 조용히 끝내지 않는다. 기대와 다르면 그것 자체가 신호다.
    raise SystemExit(
        f"입력 파일 없음: {EXPORT_DIR} — 마지막 성공 {last_success_date()}"
    )

processed = ingest(files)
if processed == 0:
    raise SystemExit(f"{len(files)}개 파일을 찾았으나 적재된 행이 0건")

print(f"OK: {len(files)}개 파일 / {processed}행 적재")
```

핵심은 **"아무 일도 일어나지 않음"을 성공으로 처리하지 않는 것**입니다. 정기 작업은 매번 뭔가를 해야 하는 게 정상이고, 안 했으면 그게 이상한 겁니다.

## 왜 한 달이나 몰랐나

세 가지가 겹쳤습니다.

첫째, **알림이 성공 경로에만 붙어 있었습니다.** 리포트를 만들어 메신저로 보내는 작업이었으니, 성공하면 메시지가 오고 실패하면 아무것도 안 옵니다. 그런데 "메시지가 안 온 날"과 "오늘은 보낼 게 없는 날"을 사람이 구분하지 못합니다. 알림은 결과가 아니라 **실행 자체**에 붙어야 합니다.

둘째, **로그를 찾아볼 생각을 안 했습니다.** 실행 기록은 잘 쌓이고 있었습니다. 62개 파일이 디스크에 그대로 있었습니다. 아무도 안 읽었을 뿐입니다. 쌓기만 하고 집계하지 않는 로그는 없는 것과 같습니다.

셋째, **연속 실패를 세지 않았습니다.** 한 번 실패는 일시적 문제일 수 있지만 6번 연속은 구조적 고장입니다. 이 둘을 같은 취급하면 안 됩니다.

## 그래서 어떻게 바꿨나

작업별로 이 세 줄을 추가하는 것으로 대부분 해결됩니다.

1. **실행할 때마다 한 줄 요약을 남긴다.** 성공이든 실패든, 무엇을 몇 건 처리했는지. 출력이 비면 그 자체를 실패로 본다.
2. **연속 실패 N회를 별도 알림으로 올린다.** 개별 실패는 로그로 충분하지만, 연속 실패는 사람을 불러야 한다.
3. **주 1회 전체 작업의 마지막 성공 시각을 집계해서 받는다.** 개별 알림이 아니라 "최근 7일 한 번도 성공 못 한 작업" 목록.

세 번째가 특히 효과적입니다. 실패 알림은 놓치지만, "이 작업은 12일째 성공 기록이 없습니다"라는 한 줄은 놓치기 어렵습니다.

## 정리

- 자동화의 기본 실패 모드는 에러가 아니라 **침묵**이다.
- 전체 성공률은 죽은 작업을 가린다. **작업 단위 성공률**을 따로 봐야 한다.
- "할 일이 없었다"를 성공으로 처리하면 장애가 영구히 숨는다.
- 알림은 결과가 아니라 실행에 붙이고, 연속 실패는 개별 실패와 다르게 취급한다.
- 사람이 확인하는 경로와 자동화가 쓰는 경로가 다르면, 자동화 경로로 검증해야 한다.

모니터링을 붙이기 전까지, 제가 "잘 돌고 있다"고 믿었던 근거는 실제로는 "불평이 없었다" 뿐이었습니다. 그건 근거가 아닙니다.
